# Що знайдено і чого бракує реальному EDC16U34-флешеру

Дата: 2026-10-01. Обсяг: локальні артефакти, аудит Android/Termux і первинний відкритий код. Жодної операції з USB/ADB/живим ECU не виконано. Production-код, прапорці допуску і прошивки не змінені.

## 1. Seed/key знайдено для точного заводського софту

Попереднє твердження «алгоритму немає, відновити його неможливо без реальних пар» було передчасним. Джерело вже лежало локально:

`D:\golf5-ecu-system\diagnostic-review\definitions\03G906021QJ_1984_391847_P447_HAXN_EDC16U34_3.42\03G906021QJ_1984_391847_P447_HAXN_EDC16U34_3.42.sgm`

Рядок 56, тег `KWP-2000-SA2`:

```text
68 05 81 4A 05 87 0A 22 12 89 49 4C
```

Ідентифікація контейнера: `03G906021QJ`, upgrade `1984`; файл лежить у комплекті exact-SW `391847`. Повний той самий дванадцятибайтовий скрипт знайдено у заводському BIN за файловими зміщеннями `0x03D3FA` і `0x03F1FA`. Заводський BIN реконструйовано з HEX; його SHA-256: `cf891152a97fb63609b40fc590fd86f38b034119b516e936eb8c0173e2551d26`.

SA2-декодування: п'ять повторень rotate-left на один біт; коли попередній старший біт був 1, застосувати XOR `0x0A221289`. Арифметика unsigned 32-bit; seed/key передаються як чотири байти з узгодженим порядком байтів.

```python
for _ in range(5):
    carry = seed >> 31
    seed = ((seed << 1) | carry) & 0xFFFFFFFF
    if carry:
        seed ^= 0x0A221289
```

Декодування звірено з [SA2 VM автора Brian Ledbetter](https://github.com/bri3d/sa2_seed_key/blob/master/sa2_seed_key/sa2_seed_key.py): 10 007 seed, нуль розбіжностей. Приклади `12345678 -> 52CEEA10`, `FFFFFFFF -> 3A203E98` є **синтетичними обчисленнями**, не захопленими сесіями ECU. VM збережена з MIT LICENSE та хешем. Відтворення: `python docs/research/2026-10-01/extract_exact_sgm.py`.

Статус: **EXACT_CONTAINER_DOCUMENTED + FACTORY_BIN_MATCH + OFFLINE_VM_CROSSCHECKED**. Прийняття живим ECU: **NOT TESTED**. Потрібно встановити правильну сесію, рівень доступу, формат відповіді й відповідність поточного завантажувача заводському профілю. Прапорець `verified` не перемикали.

Поточний `security/LegacyBlsSecurityAlgorithm.kt:5` має `verified=false` і зовсім іншу формулу: XOR `4F73A1B2`, rotate-left 5, XOR `35A9C2E1`. Вона не є реалізацією знайденого SA2-скрипту.

## 2. Заводська геометрія й додаткова контрольна сума встановлені

Витяг із XML, межі включні:

| SGM-блок | Стирання | Дані / перевірка | Довжина даних | SGM CHECKSUMME |
|---|---|---|---|---|
| dav_pfu_01 | 010000–03FFFF | 010000–03FEFF | 02FF00 | 8F04 |
| dav_pfu_02 | 040000–17FFFF | 040000–17FFFF | 140000 | 225D |
| dav_pfu_05 | 180000–1BFFFF | 180000–1BFFFF | 040000 | EE55 |
| dav_pfu_04 | 1C0000–1FFFFF | 1C0000–1FDFFF | 03E000 | 73BA |

У всіх чотирьох блоках `sum(plaintext_bytes) & 0xFFFF` заводського BIN точно збігається з `CHECKSUMME` у SGM. Це окремий контейнерний контроль, відмінний від additive32 residue `D01FE500` у калібруванні.

Для двох калібрувальних блоків стирається загалом `0x80000` байтів, а контейнер передає `0x7E000` байтів. Хвіст `1FE000–1FFFFF` (8 KiB) у контейнері не передається. Не можна автоматично переносити поточний запис усіх 512 KiB на цей заводський шлях або очікувати SHA-256 рівність хвоста без визначення його постстирального вмісту.

`dav_pfu_*` — назви контейнера, не підтверджені номери USB-команд чи лічильники `TransferData`. Розмір пакета 128 байтів заводським XML не встановлено. Raw timing-поля та всі хеші містяться в `exact-sgm-evidence.json`; їхні одиниці не вгадували.

## 3. Є відкритий код сімейства EDC16, але він потребує адаптації

[fjvva/ecu-tool, ECU_Flasher_UNO_EDC16.ino](https://github.com/fjvva/ecu-tool/blob/master/Portable%20Firmware/HW%20V2/ECU_Flasher_UNO_EDC16/ECU_Flasher_UNO_EDC16.ino) заявляє EDC16U31/U34. Його `LVL1Key` використовує половини константи `0A22/1289`; окремий шлях читання використовує інший рівень доступу. Запис містить стирання, перевірку завершення і перетворення даних. Це корисний кандидат для аналізу протоколу, але не доказ працездатності на нашому конкретному ECU або MPPS v18.

Цей код показує, що для адаптації треба розібрати:

- read security `27 03/04` проти write security `27 01/02`; кандидат для читання має `seed+2FC9`;
- блоки за адресами `1C0000` та `180000`, з різними довжинами;
- routine `31 C4` та опитування `33 C4` для стирання;
- routine `31 C5` та `33 C5` для контролю після передачі;
- формат download, представлення зашифрованого потоку і ACK/лічильники;
- зміну швидкості й умов доступу.

Це перелік напрямів адаптації, не інструкція для запуску на автомобілі. Сумісність та права на інтеграцію чужого коду треба встановити окремо; файл збережено як дослідницький матеріал.

Наявний readback від 2026-09-23 повторно перевірений: SHA-256 `a3c1c40dc378197da7863d22978055eea4669574b704b44f3935c2a7db55de27`, файл 2 MiB, діапазон `000000–17FFFF` увесь `FF`. Це **не повна recovery-копія**. Перевірено вміст локального файлу; нового фізичного читання не проводили.

## 5. Конкретні дефекти поточного коду

Усі посилання нижче відносні до `C:\Users\pavlo\golf5-android-flasher`.

1. **Тестований writer не підключено до UI.** `MainActivity.kt:634` створює `EcuFlasher`, рядок 648 викликає `flashFirmware`. `FlashTransaction` реалізує автоматичний backup і окремі стадії, але цим шляхом не використовується. UI перевіряє ручний session-backup, тому автоматичний цикл із тестів не дорівнює поведінці екрана.
2. **Операції не мають профільної геометрії.** `Kwp2000Protocol.kt:192` і `EcuFlasher.kt:53` запитують одним блоком повні 512 KiB. У production writer немає `31 C4/C5` та перетворення потоку. Це конфлікт із знайденими джерелами, який потрібно розв'язати до допуску до запису.
3. **Некоректні підтвердження успіху.** `EcuFlasher.kt` ігнорує Boolean результат `sendSecurityKey`, `requestDownload`, `transferData`. `FlashProtocolAdapter.kt:24` повертає true після `sendSecurityKey`, навіть якщо той повернув false; рядок 35 ігнорує результат download і повертає фіксовані 128 байтів.
4. **Backup потребує read-профілю.** `FlashTransaction` читає backup перед власною programming/security-стадією. Це не доказ неправильності на кожному ECU, але підготовлена read-сесія й read-access не встановлені його контрактом. `MainActivity.startReading` також не встановлює окремий read Security Access.
5. **Fail-closed не наскрізний.** Екран блокує поточний unverified legacy-алгоритм; прямий старий writer і Termux не забезпечують той самий допуск. `TermuxBridgeServer.kt:101` і далі має raw/control-команди без профільного flash gate. Прив'язка до loopback не робить довільну команду ECU перевіреною.
6. **Termux потребує окремого завершення.** У `termux/edc16_flasher.py:265` identity guard з `and` пропускає випадок збігу лише одного ID. Немає рівноцінних voltage/auth/backup/readback gates. Текст README про готовий запис не підтверджений поточним кодом.
7. **Профіль write-readback не враховує хвіст.** Потрібно визначити expected post-write образ для 8 KiB, що стираються, але не передаються у заводському контейнері; checksum32 і SHA-256 усього прочитаного регіону виконують різні ролі.

## 6. Перевірки й рішення

- `extract_exact_sgm.py`: PASS, 10 007 VM-порівнянь; повна SA2 tape збігається із заводським BIN двічі; 4/4 SGM byte-sum16 збігаються.
- JVM-тести реально перезапущено після очищення результату: **58 tests, 0 failures, 0 errors, 0 skipped**.
- Команда: `gradlew.bat "-Dorg.gradle.java.home=C:\Program Files\Eclipse Adoptium\jdk-17.0.20.101-hotspot" :app:cleanTestDebugUnitTest :app:testDebugUnitTest --console=plain`.
- Перша спроба з Java 11 не запустила тести; для повтору використано вже встановлений Java 17, глобальні налаштування не змінено.
- Hardware authentication, ECU ID/read/erase/write/readback у цьому аудиті: **NOT RUN**.

Gemini виконав незалежний read-only аудит. Його висновки перевірено за файлами. Не прийнято твердження, ніби gateway orientation доводить фізичний CAN/K-Line, ніби ECU seed/key досі відсутній, або ніби довільна read-сесія гарантовано поверне певний NRC. Gateway підтверджує локальні артефакти, не живий транспорт.

Наступний конкретний етап: інтегрувати документований SA2 й exact-profile geometry як окремий недопущений до physical-write профіль; виправити ACK/транзакцію/Termux; установити USB handshake та read-only ID/backup на власному адаптері. Для завершення програмування потрібен підтверджений write protocol або його аналіз із відповідного loader/tool trace, стендове write/readback і власний recovery backup. Не можна чесно назвати ці фізичні докази «знайденими в інтернеті».

Алгоритм і геометрія більше не є невідомими заводськими даними. MPPS v18, live-послідовність і реальна валідація залишаються незакритими.
